# Savia interface integration

5 October 2026 (America/Bogota)

Savia is the customer's assistant and owns the problem until it is resolved. The customer talks to one assistant; Savia understands intent, criticality and mood, resolves immediately when possible, or requests a specialist team and returns its reviewed synthesis. If completion needs a human, Savia creates a ticket through the existing integration with context, evidence and attempted actions, then continues the customer's status and follow-up.

The visual reference remains FLUJO World: black and white eyes in a playful physical world, with animated details and floating windows. The opening shows little information. Team activity, evidence, history, transcripts and timelines appear when useful; technical operator controls remain available through Flujo. New visual and interaction work is authored by Claude Opus at High effort.

The existing [Flujo world implementation](https://github.com/mario-andreschak/FLUJO/pull/560) supplies model setup, real work, voice and precise controls. The portable presentation package displays host-approved observations; task intake, authentication and execution belong to its host. Reuse the existing website/avatar, FLUJO foundation and O/FACTORY/Seagulled coordination, rather than creating a replacement orchestration engine. Integration must retain the complete workflow described in [the vision](VISION.md).

## One assistant and the existing swarm-teams route

Reuse the recovered Claude swarm-teams implementation directly: `swarm_agent`, `swarm_team`, `swarm_supervisor` and `swarm_boot`. The installer compiles the FlowSpecs through FLUJO's API. `flujo-cloud` clones the tool-free boot workspace, then the installer adds the tool/team flows to the ready worker. Roles, problem-specific instructions and model/tool bindings specialize these existing flows; no additional role-manifest project is a prerequisite.

The human's exact target is ten Fly FLUJO Machines, each running **one lead plus nine specialist conversations**: ten conversations per Machine and 100 other AIs across the fleet, with Savia's root supervision separate. The stock `swarm_team` subflow has `concurrencyLimit: 10`; specialize the selected Savia team prompt and native subflow bound to nine children. This changes the selected existing FlowSpec, not the template framework. Within a worker, native `start_subflow_*`, `subflow_send_message` and `subflow_wait` staff, steer and collect agents. Across workers, fleet delegation/message/wait, `board_post`/`board_read` and relay share findings and challenge conclusions. Text task/message/result communication is sufficient between agents.

The interface consumes existing runtime observations and ticket/notification results. This table identifies what to reuse, not a new wire API, manifest or scheduler:

| Host-owned information | Interface behavior |
| --- | --- |
| Canonical problem/task and customer conversation references | Keep one Savia conversation through immediate answers, investigation, review, human handoff and follow-up. Preserve native conversation, accepted-task and gateway-job identifier domains. |
| Existing flow, fleet goal/run, worker and installation references | Use the recovered installer/clone route and show its recorded outcome. A requested template or concurrency limit is not a running team. |
| Native child-conversation identities, assigned tasks/roles, installed Flow model/tool bindings, board findings and review relationships | Show actual cooperation when requested. Specialize tasks through existing team prompts; private instructions, credentials and tool arguments remain behind host permissions. |
| Actual Fly Machine count, all lead/child conversation IDs, configured limits, active/queued/completed counts and inference availability | Count each Machine's one lead and nine specialists toward its ten members. Keep Savia's root supervisor separate. Record actual concurrent states and preserve the ten-Machine × ten-conversation target independently of available capacity; a smaller or queued deployment does not qualify it. |
| Actual findings, evidence references, disagreements, review outcome and synthesized result | Savia reports the reviewed conclusion and relevant uncertainty. Progress and success require canonical recorded outcomes. |
| Existing human ticket reference, context/evidence/attempted-action record and current handoff state | Keep the problem open for Savia's status and follow-up; creating a ticket does not itself resolve it. |
| Existing session, push or email delivery result and follow-up state | Show the customer's actual update and delivery state. UI rendering is not proof that a notification was sent. |

Savia's customer-visible lifecycle is intake, clarification when needed, immediate resolution or team investigation, review and synthesis, then resolution or tracked human handoff with follow-up. These labels project existing backend state; they do not create a parallel lifecycle ledger. Customer website/avatar/voice work remains with its current owners. The inter-agent text path does not remove the supported customer text or voice capabilities.
